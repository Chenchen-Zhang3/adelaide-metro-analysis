# Adelaide Metro application — developer handover

## Source ownership

The team's GitHub repository is the source of truth. The application is editable HTML/CSS/JavaScript (frontend) and Python/Flask (backend); no code exporter is required. Merge reviewed feature branches into `main` before release. Never commit personal data files, API secrets, or large historical SQLite databases.

## Requirements for local development

- Python 3 with the packages imported by the backend, including Flask, Flask-CORS and `gtfs-realtime-bindings` (provides `google.transit.gtfs_realtime_pb2`). Install the full project's pinned dependency list when the team provides one.
- A valid approved historical SQLite database and permission to use it.
- A published static GTFS catalogue matching the historical analysis period.
- A modern browser and internet access for map tiles.

## Start the application

From the repository root, in Terminal 1:

```sh
export ADELAIDE_METRO_DATABASE_PATH="/absolute/path/to/approved-history.db"
export ADELAIDE_METRO_STATIC_MAP_DATA_PATH="/absolute/path/to/generated-static-catalog"
unset ADELAIDE_METRO_DEMO_MAP_DATA_PATH
python3 -m flask --app backend.api.app run --host 127.0.0.1 --port 5001
```

In Terminal 2:

```sh
python3 -m http.server 8000 --bind 127.0.0.1 --directory frontend
```

Open `http://127.0.0.1:8000`. Both terminals must stay running; a browser 'cannot connect' error usually means the frontend server is stopped. Flask's development server is **not** a production deployment method.

## Data catalogue

The static catalogue is generated by `backend.services.static_map_data` from an authorised GTFS static ZIP. Its version, agency selection and route types must match the expected analysis. See the module's CLI `--help` and repository documentation for its supported flags. Do not distribute the original database or static ZIP without permission.

## Verification before client acceptance

1. `GET /api/stops` and `GET /api/routes` return the expected published catalogue.
2. Select a stop: confirm popup, associated route information, and location selection.
3. Grant browser location permission: verify the nearest-stop calculation and marker.
4. Load a route and confirm its geometry and stop list.
5. Load historical predictions for a known populated 15-minute Adelaide time window at minimum samples 1 and 10; confirm route-specific and network-wide modes, counts, marker colours and missing-data states.
6. Change route or time while a request is pending; confirm no stale markers remain.
7. Verify historical playback, hotspots and performance controls still work when delay mode is switched off.
8. Validate any punctuality metric against its definition: **historical GTFS-Realtime predictions are not verified actual arrivals**.
9. Run automated tests with all backend dependencies installed; record failures and any unavailable external data.

## Known limitations

- The browser overlay shows historical *predicted* delays, not measured arrival-time differences.
- Data coverage depends on the approved historical database and static catalogue; missing data is not zero delay.
- The frontend API base URL currently points to `127.0.0.1:5001`; production deployment needs an environment-specific configuration and hosting/security review.
- The approved database and generated catalogue are not part of the frontend feature commit.

## Updating the application

Edit the relevant source file in the team's repository, run syntax and integration checks, commit to a feature branch, open a pull request and merge after review. Maintain a reproducible dependency manifest and data-provisioning procedure before final client delivery.
